AI Systems Engineering & Evaluation Lab

An agent system that answers questions and takes actions over the handbook, runbooks and policies of a fictional software company, laid out the way I inspect one. Retrieval, tool execution, permission checks, injection screening, approval gates, retries and scoring are real code running in this page. No language model runs here. The model's outputs come from a deterministic rule-based stand-in that selects answer sentences from retrieved passages and routes requests to tools by pattern. The tool backends (service status, tickets, config) are simulated. Latency, token and cost figures come from a cost model whose prices and per-step latencies are assumptions.

    Tool failures and recovery

    Every tool call except the calculator, including knowledge base search, fails with the seeded probability set by the tool failure rate in the Run and trace configuration. A failure is a timeout or an HTTP 503. The executor retries with exponential backoff and jitter, and a circuit breaker per tool fails fast after repeated failures. The sweep reruns all cases at each failure rate.

    How it works

    Method, formulas, assumptions and limits
    • The orchestrator receives a task and a role. The planner stand-in routes it by pattern: an answer from the knowledge base, a calculation, a read-only status check, or a side-effect tool (open a ticket, change a config value).
    • Before any work, the executor checks that the role may call the planned tool. A role without it is blocked at once.
    • Retrieval is a tool call like any other, so it can fail and be retried. BM25 scores every chunk, the access filter drops chunks from documents the role may not read, and a heuristic reranker (BM25, idf-weighted term coverage and bigram overlap) orders the rest. It stands in for a learned cross-encoder. The top k chunks go forward.
    • The injection screen checks every sentence that would enter the context against five pattern rules. A flagged sentence is removed and quarantined, and the rest of its chunk is kept.
    • The stand-in is written to be gullible. It obeys any sentence in its context that addresses an assistant with an instruction, using a parser wider than the screen. That is how an instruction-following model fails, and it is why the screen matters.
    • The answerer picks the retrieved sentence with the highest idf-weighted coverage of the question. A calculation fills an arithmetic template from the question and one retrieved sentence and sends the expression to the calculator tool.
    • The verifier scores how well the cited chunks cover the question, counting words the knowledge base never uses at the highest idf. Below the threshold it rejects the draft and the orchestrator refuses. For a calculation it also checks that the operands appear in the cited line and recomputes the result.
    • Side-effect calls stop at the approval gate. In the page you approve or reject them. In the evaluation a scripted reviewer stands in for the person: it approves a call only when it matches the case's gold call and the gold says approve, and it rejects everything else.
    • Every side-effect call carries an idempotency key, so a retry after a timeout that the backend had already applied returns the first result and creates nothing new.

    Formulas

    idf(t) = ln(1 + (N - df_t + 0.5) / (df_t + 0.5))
BM25(q, d) = sum_t idf(t) tf_t (k1 + 1) / (tf_t + k1 (1 - b + b |d| / avgdl)),   k1 = 1.2, b = 0.75
coverage(q, s) = sum_{t in q and s} w_t / sum_{t in q} w_t,   w_t = idf(t), or max idf if df_t = 0 (verifier)
rerank = 0.5 BM25 / max BM25 + 0.35 coverage + 0.15 bigram overlap
backoff_n = c_n / 2 + u c_n / 2,   c_n = min(cap, base 2^n),   u ~ U(0, 1), seeded
breaker: open after m consecutive failures; half-open after the cooldown; a failed probe reopens
citation precision = |cited and gold| / |cited|,   recall = |cited and gold| / |gold|   (documents, pooled over cases)
p95 = x_(h) interpolated, h = (n - 1) 0.95   (type 7)
tokens = ceil(characters / characters per token);   cost = (tokens_in price_in + tokens_out price_out) / 1e6
model step latency = overhead + tokens_in ms_in + tokens_out ms_out

    Assumptions

    Data and limits

    • The company, its documents, its services and every case are made up. The knowledge base has documents and chunks, so retrieval here is far easier than over a real corpus.
    • I set the answer and verifier thresholds by hand while writing these same cases. The scores are in-sample, and a held-out set would score lower.
    • The verifier checks word coverage. It cannot tell that a question asks for a name the documents never give, or about a rotation they never price, when most of the question's words are covered. Baseline cases R6 and N6 in the Evaluation tab show this.
    • The screen catches the phrasings it has rules for. One planted injection is worded so that no rule matches it, and it costs baseline case I4 its answer. I left it in because adding a rule after seeing a phrasing proves little. A real system needs more than a pattern screen: least-privilege tools, approval for side effects and output checks.
    • When the best match sits in a restricted document, the refusal says so. That tells the user such a document exists. Some teams prefer a plain refusal.
    • Latency is the sum of sequential spans under the cost model. It excludes the time a person takes to approve. Real latencies vary far more than this model.
    • None of this says how a real model would score. It shows the harness, the controls and the scoring that a real model would be measured with.
