About

I am a Quantitative Investment Professional and AI Engineer with 6+ years of experience across institutional investing, applied AI, quantitative research, and data science in the United States, Europe, and Latin America.

My work sits at the intersection of AI and portfolio management. I design and build agentic AI systems that operate inside investment workflows. Every system I build carries monitoring, guardrails, human-in-the-loop approval, and a full audit trail, because in investing an answer you cannot trace is worse than no answer.

AI systems

I build AI systems that investment teams use every day, on the models and cloud platforms large firms already run. Everything below is something I've designed, shipped and maintained.

Read it as

I design and build agentic AI systems: software agents that read documents, use the firm's own tools, check their work and hand every decision that matters to a person. For an investment team, that means the first pass on every LPA, GP report, statement and data feed is done before anyone opens the file. Analysts spend their time on judgment.

I design, build and run agentic systems in production: tool-using LLM agents with typed tool contracts, bounded autonomy, retrieval over firm documents, evaluation gates in CI and explicit human approval steps. They run inside the firm's Azure or AWS tenant and inside Microsoft 365, under the same identity, permissions and audit rules as every other system the firm runs.

What an AI agent doesThe agent loop I build on

  1. 01

    Reads

    An agent opens a document the way an analyst would. It finds the fee clause, the capital account and the NAV table, and writes down each number with the page and line it came from.

    Layout-aware parsing of native and scanned PDFs, table reconstruction and OCR where needed, then retrieval with metadata filters by fund, period and document type. Every extracted value stays bound to its source span.

  2. 02

    Uses tools

    It does not do the math in its head. It calls a calculator, a database or the firm's own models, the same tools a person would use, and keeps every result.

    Typed tool contracts exposed through Model Context Protocol servers: SQL over governed views, cash flow and pricing libraries, document search and ticketing. The model chooses the tool and the tool does the arithmetic, so numeric results are deterministic and testable.

  3. 03

    Checks itself

    Before it reports anything, it re-checks the numbers against the source and against each other. When something does not tie, it says so plainly.

    Deterministic assertions after each step: totals tie, units and currencies match, dates fall in range and every citation resolves to text that contains the value. Failed checks trigger a bounded retry or an escalation to a person.

  4. 04

    Asks before it acts

    Anything that moves money, changes a record or reaches a client waits for a named person to approve it. The agent prepares the work and a person signs it off.

    Approval is a first-class step. Actions are drafted as proposals with evidence attached, routed by risk tier and executed only after sign-off. The approver, the time and the exact change are written to an append-only log.

What I build

Document intelligence

My systems read LPAs, GP reports, capital account statements, DDQs and CIMs and pull out the figures a team needs: fees, commitments, NAVs, cash flows and key terms. Every number links back to the page and line it came from, so an analyst can check it in seconds. That turns days of manual data entry into a review of exceptions, and it gives the team one source of truth across GPs that all report differently.

Layout-aware parsing of native and scanned PDFs, table reconstruction across page breaks, and extraction into typed fields with units, currency, period and fund identity normalized. Each value carries a page and line reference and is verified against the source text before it is accepted. Values that fail are held for review and never imputed. Field-level accuracy and citation coverage are tracked per document type and per GP template, because a new template is where extraction quality usually drops.

See it in Private Capital Lab and Fund Terms Auditor

Agent workflows

Multi-step systems that research, monitor and reconcile across sources, so analysts start the day from the exceptions. One agent can read a capital call, match it to the books, check it against the liquidity plan and draft the cash movement. It stops for a person to sign off before anything moves money or reaches a client.

Tool-using agents built on the Claude Agent SDK and Model Context Protocol servers, with scoped tools, step and token budgets, explicit stop conditions and hard checks between steps. I use fixed workflows where the path is known and give the model freedom to branch only where the task needs it. Every run is traced and can be replayed from its log with the same inputs, tools and model version.

See it in Agentic Portfolio Monitoring

Evaluation and quality

Every system is tested on hand-labeled documents for accuracy, citation coverage and false flags. Any change is retested before it ships, so a team knows the error rate before it relies on the output. The same test set is how I decide whether a new model is better or just newer.

Hand-labeled gold sets per document type, stratified by GP template and including planted errors, versioned with the code. Scoring covers field accuracy within tolerance, citation coverage, recall on planted issues and false-positive rate, plus tool-call validity for agents. The regression suite runs in CI on every model, configuration or code change, and a release ships only if no metric drops.

Governance and security

Each user reaches only the data they are allowed to see, and every action leaves an audit trail. Sensitive data stays inside the firm's own cloud tenant, with a clear record of which model did what and who approved it. That is what lets compliance and risk teams say yes.

Entra ID single sign-on and role-based access, with each user's permissions carried into search so a model never reads what that user cannot open. Private networking, managed secrets and customer-managed keys in the firm's Azure or AWS tenant. Append-only logs record model, version, inputs, outputs, tools called and approver for every action, retained under the firm's records policy.

Data foundations

I connect portfolio systems, accounting, market data vendors and data warehouses into one reconciled source. Models then work from the same numbers the investment and operations teams sign off on. Without this, AI just produces faster versions of the same spreadsheet disagreements.

Feeds from portfolio, accounting and market data systems land in Snowflake or PostgreSQL, scheduled with Airflow and modeled in dbt with tests on keys, freshness and reconciliations. Agents read governed views through typed tools, never raw tables, so every number traces back to a source system and a load time. Extracted document data flows back into the same models with its citations attached.

Quant and machine learning models

Forecasting, regime models and portfolio optimization built for allocation decisions. This includes my published research on deep learning for multi-asset portfolios. Agents call these models as tools, so a recommendation rests on tested math and the language model only explains it.

An example workflow: a capital call

How an agentic system handles one routine task from inbox to books, with a person in charge of the only step that moves money.The same task as a run: trigger, extraction, controls, proposal and execution, each step traced and replayable.

  1. 1

    A notice arrives

    A GP emails a capital call notice. The system picks it up from the shared mailbox within minutes.

    A Microsoft Graph subscription on the operations mailbox triggers the run. The attachment is classified and de-duplicated by content hash, so a resent notice is processed once.

  2. 2

    Read and match

    It reads the amount, due date and wire details, matches them to the right fund and commitment in the books and checks the amount against the unfunded commitment.

    Typed extraction with citations, entity resolution of fund and LP names against master data, and reconciliation of the requested amount against the commitment ledger through a SQL tool.

  3. 3

    Check the cash

    It checks the amount against cash on hand and the liquidity plan and flags anything unusual, such as changed wire instructions.

    Rule checks on unfunded balance, due-date window and liquidity buffer, plus an anomaly check on bank details. Any change to wire instructions blocks automation and forces a call-back control.

  4. 4

    Prepare the work

    It drafts the cash movement and the accounting entry, with the notice attached and every number linked to its source.

    A proposal record with evidence, citations and a risk tier is written to the queue and posted to Teams as an approval card with approve and reject actions.

  5. 5

    A person approves

    Operations reviews and approves. The system books it, files the notice and updates the pacing model.

    On approval, idempotent writes go to the accounting system and the warehouse, the pacing model refresh is scheduled and the run trace is sealed in the audit log.

How I run AI in production

The engineering that makes these systems safe to rely on. Use the switch above for plain or technical detail.

Grounded answers

Every answer comes with the passage it rests on, so nobody has to trust a summary they cannot check. If the system cannot find support in the documents, it says it does not know.

Hybrid retrieval, keyword and vector search together, over chunked documents with metadata filters by fund, period and document type, then reranking. Generation is limited to retrieved passages, and an answer without a resolving citation is withheld.

Typed, checked outputs

Numbers come out in the right units and periods, ready to drop into a model or a report. Nothing is quietly filled in when a value is missing.

Extraction targets typed fields with explicit units, currency and period. Outputs are validated before anything uses them. A field that fails is retried a bounded number of times with the error attached, and then routed to a person.

The right model per task

Fast, inexpensive models handle routine work. The strongest models handle the hard reading. That keeps quality high and the bill predictable.

Per-task routing on measured accuracy, cost per document and latency at the median and the tail. Context caching for long documents, batch runs for overnight volumes and a token budget per workflow with alerts when it is exceeded.

Inside Microsoft 365 and Teams

People use the tools where they already work, in Teams, Outlook and SharePoint. Nobody has to learn a new app or copy files around.

Copilot agents and Teams apps that read SharePoint, OneDrive and Outlook through Microsoft Graph on behalf of the signed-in user, so the model sees only what that person can open. Approvals arrive as Teams cards and their outcome is logged.

Data stays in the firm

Sensitive data stays inside the firm's own cloud and never trains anyone else's model.

Private networking, managed secrets and encryption keys in the firm's Azure or AWS tenant, with zero-retention terms on hosted model endpoints. Personal data is redacted before any call that leaves the tenant, and open-weight models run in-tenant when data cannot leave at all.

Observability

Every run can be traced, costed and replayed after the fact, which is what auditors and risk teams ask for first.

Structured traces per run with model, version, inputs, outputs, tools called, latency and cost. Dashboards per workflow, and alerts when accuracy on live spot checks, cost or response time moves outside agreed bands.

Reliability

If a model provider has an outage, the work still gets done.

Timeouts, retries with backoff and jitter, provider and model fallbacks, durable queues and idempotent actions, so a failed step can be rerun without posting anything twice.

Release discipline

Nothing changes in production until it passes the tests, and every change can be undone.

Labeled regression sets run in CI on every change. A new model runs in shadow next to the current one before any switch, and every release has a documented rollback.

From idea to production

How I take an agent from a conversation with the team to a system they rely on.

  1. 01

    Start from the decision

    I sit with the team and map the decision, the documents behind it and where the hours go today.

    A written spec of inputs, outputs, tolerances and failure modes, and a split between the steps that must stay deterministic and the ones that need a model.

  2. 02

    Build the answer key

    We label a set of real documents by hand, so everyone agrees what right looks like before anything is built.

    A stratified gold set by document type and template, labeled for values, citations and planted errors, versioned alongside the code.

  3. 03

    Ship the smallest useful version

    The first version covers the most common case and shows its work on every number.

    Start from a fixed workflow and typed tools, and add agent autonomy only where the task needs branching.

  4. 04

    Measure and improve

    Every version is scored against the answer key, and the worst errors get fixed first.

    Error analysis by field and template, regression tracking in CI and model comparison on the same set under cost and latency budgets.

  5. 05

    Run it in the background

    The system runs next to the team for a few weeks without acting, so everyone sees how often it is right.

    Shadow mode with observe-only permissions, tracking agreement with the people doing the work per field and per action before anything is automated.

  6. 06

    Go live with guardrails

    It goes live with approvals on every action that matters, and we keep measuring after launch.

    Risk-tiered autonomy, approval gates, alerting on metric drift and a rollback path for every release.

How I pick the right model

Each task gets the model that fits it. I judge every candidate on accuracy on the firm's own documents, cost per document, speed and where the data is allowed to go. Frontier models like Claude and OpenAI's models take the long documents and the hard reasoning. Open-weight models run where data has to stay inside the firm or where volume makes cost the deciding factor. No model goes into production, and none gets swapped in, until it beats the current one on a labeled test set.

For each candidate I run the labeled set and record field accuracy, citation accuracy, tool-call validity, latency at the median and the tail, and cost per document. Long-context frontier models handle full LPAs and reasoning across several documents. Smaller, faster models handle classification, routing and first-pass extraction. Open-weight models run in-tenant for restricted data, sized to the hardware the firm has. Structured outputs and tool calls are checked on every call whatever the model, and a model is promoted only when it wins on the labeled set at an acceptable cost.

What makes it production-grade

  • Tested on labeled documents before every release
  • Human approval on anything that moves money or reaches a client
  • Full audit trail of every action and every model output
  • Access limited to the data each user is allowed to see
  • Cost and response time monitored per workflow
  • Fallbacks when a model or provider is down

Measured on the demos on this site

How these are measured
Extraction accuracy
Share of hand-labeled fields where the extracted value matches the label within a stated tolerance.
Citation coverage
Share of extracted values whose page and line reference points to text that actually contains the value.
Planted issues caught
Errors placed in the documents on purpose, such as a wrong fee or a broken roll-forward, that the system flagged for review.
False-flag rate
Share of clean checks that were flagged anyway. A useful system keeps this near zero so reviewers trust the flags.
