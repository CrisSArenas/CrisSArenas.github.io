Guide — Agentic Portfolio Monitoring

1 · What you are looking at

Portfolio monitoring is a good fit for agents and a bad fit for a chatbot. The work is continuous, it is rule-bounded, it spans a dozen unrelated data sources, and the output is a short list of things a human needs to decide. It is also the part of the job where a mistake is expensive and an unexplained action is unacceptable — which is why most of the engineering here is about controls, not about the model.

Press Run monitoring cycle. Thirteen agents execute as a dependency graph. The six detection agents are independent and run concurrently; everything downstream of triage is sequential because each stage consumes the last one’s output. What you get at the end is a finding register, a costed remediation queue, and an audit trail.

3 · Autonomy, and why the default is not the highest one

Three levels. Observe only detects and explains, and proposes nothing — the right setting for the first months of a deployment, when you are measuring the false-positive rate. Propose and await approval is the default: every trade is drafted, costed and pre-checked, and a human clicks. Auto-execute small and low-risk releases proposals that clear all of a notional cap, a severity cap and a post-trade clean re-check.

Two hard gates sit above the autonomy setting and cannot be overridden from the UI:

  • The data-quality gate. If any mark is stale, nothing auto-executes at any autonomy level. An agent acting confidently on a price from yesterday is the single most expensive failure mode in this design, and the cheapest one to prevent. Run the pricing-feed outage event and watch every proposal fall back to manual.
  • The non-tradeable gate. A breach in private equity or real assets cannot be fixed by a trade. The planner says so and proposes a pacing action for the committee instead of inventing an order. An agent that produces a plausible instruction for an impossible trade is worse than one that produces nothing.

5 · The economics

The cost panel is the part most demonstrations leave out, and it is usually what decides whether a fleet ships. A cycle here runs about 54,000 tokens for roughly $0.43. Routing every role to a frontier model would be the obvious build and 2.9× the cost; the detection agents are doing structured comparison against numeric limits, which a fast model does as well and far cheaper. The frontier model is reserved for the planner, which is the one role that has to reason about several constraints interacting.

The other number that matters is the critical path. Total agent work is well over the cycle’s wall-clock time because the six detection agents overlap. Running them sequentially would roughly double the latency for no benefit.

6 · What is simulated and what is not

No model is called. There is no API key on this page and no network request leaves it. The agents are deterministic functions with scripted latencies and token counts; the “reasoning” in each finding is generated from the rule that fired and the numbers that fired it. What is real is the architecture: the dependency graph, the gating, the post-trade re-check, the approval routing and the hash chain are the ones I would build.

The portfolio is synthetic. A $1.0bn book across eight sleeves with eight look-through issuers. It resembles an institutional multi-asset mandate; it is not one.

The cost figures are illustrative. Tier prices are round numbers chosen to show the shape of the routing decision, not a current price list.

Methodology & assumptions

What this models

A production-shaped control loop for agentic portfolio oversight. A fleet of thirteen role-scoped agents executes as a dependency graph over a synthetic $1.0bn multi-asset book: six independent detection agents check investment-policy ranges, ex-ante tracking error, liquidity, single-issuer concentration, corporate actions and data quality; a triage agent de-duplicates and assigns severity; a planner drafts remediation; an estimator costs it; a compliance simulator re-runs every rule against the post-trade book; a router applies the autonomy policy; and a logger writes a hash-chained audit record. Events can be injected to create genuine breaches, and approvals genuinely change the book and re-trigger detection.

Key assumptions

  • Eight sleeves with policy weights 25/15/10/25/5/10/8/2 and per-sleeve IPS ranges; illiquid sleeves are private equity and real assets, capped at 25% combined.
  • Liquidity is tested as the share of NAV realisable inside a 10-business-day horizon, against a 70% floor. The obvious alternative — days to liquidate 90% of the book — cannot be satisfied by any portfolio holding 14% in privates, and a limit that can never pass is noise on the board rather than a control.
  • Ex-ante tracking error is √(a′Σa) on active weights a = wp − wpolicy, with a long-run covariance built from sleeve volatilities and a fixed correlation matrix.
  • Trading cost is a half-spread plus a square-root impact term, both scaled by sleeve liquidity: 4bp all-in on developed equity rising to 38bp on high yield. Private sleeves are marked non-tradeable rather than given a price.
  • Agent latencies and token counts are fixed per role. Cycle wall-clock is the longest path through the DAG; cycle cost is the sum over all agents of input and output tokens at the tier price.
  • The audit digest is a 32-bit FNV-1a over the previous digest concatenated with the entry, rendered as eight hex characters. It demonstrates chaining; it is not a cryptographic commitment and would be SHA-256 in anything real.
  • Everything is deterministic. The same sequence of events and clicks reproduces the same book, the same findings and the same chain.

Design decisions worth naming

  • Detection is deterministic; only planning is generative. Limit checks are arithmetic and belong in code, where they are testable and cannot hallucinate. The model is used where judgement is needed — drafting a remediation that respects several constraints at once — and its output is then re-checked by the same deterministic rules.
  • The post-trade simulator is not optional. Rebalancing to fix one breach very often opens another: funding an equity top-up out of cash breaks the cash floor. The simulator catches that before a human sees the proposal, so the human is reviewing judgement calls rather than arithmetic.
  • Data quality gates execution, not detection. Stale marks should not stop you from looking — they should stop you from acting. Detection continues and is labelled provisional; auto-execution stops dead.
  • Every finding names the agent that raised it. Attribution is what makes a false-positive rate measurable per role, which is what lets you tune or retire an agent instead of the whole fleet.

Limitations — read these before you read the numbers

  • No model is called anywhere on this page. The agents are deterministic functions with scripted latency and token counts. This demonstrates an architecture and a set of controls; it does not demonstrate model quality, and it cannot tell you anything about how a real LLM would behave on these tasks.
  • Token, latency and cost figures are illustrative. They are chosen to show the shape of the routing trade-off. Real numbers depend on prompt design, context length, caching and the provider’s price list.
  • Risk is a static long-run covariance. Volatilities and correlations do not move with the market, so the tracking error after an injected sell-off understates what a real risk model would print, because correlations rise in exactly those weeks.
  • Trading costs are a stylised function, not a broker estimate, and there is no modelling of settlement, borrow, tax lots, wash sales or minimum lot sizes — all of which constrain real remediation.
  • The false-positive rate is not modelled. In a real deployment it is the number that decides whether the fleet is used or ignored, and you only learn it by running in observe-only mode against a human baseline for months.
