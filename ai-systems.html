01

Agentic AI systems

An agent is a model that can use tools and check its own work. Several of them, each with a narrow job, can do the first pass on work an analyst would otherwise start from a blank page.

Agentic systems built from narrow, tool-using workers under an orchestrator, with deterministic checks between steps, an independent verifier and an explicit approval gate.

What a single agent does

  1. 01

    Reads

    An agent opens a document the way an analyst would. It finds the fee clause, the capital account and the NAV table, and writes down each number with the page and line it came from.

    Layout-aware parsing of native and scanned PDFs, table reconstruction and OCR where needed, then retrieval with metadata filters by fund, period and document type. Every extracted value stays bound to its source span.

  2. 02

    Uses tools

    It does not do the math in its head. It calls a calculator, a database or the firm's own models, the same tools a person would use, and keeps every result.

    Typed tool contracts exposed through Model Context Protocol servers: SQL over governed views, cash flow and pricing libraries, document search and ticketing. The model chooses the tool and the tool does the arithmetic, so numeric results are deterministic and testable.

  3. 03

    Checks itself

    Before it reports anything, it re-checks the numbers against the source and against each other. When something does not tie, it says so plainly.

    Deterministic assertions after each step: totals tie, units and currencies match, dates fall in range and every citation resolves to text that contains the value. Failed checks trigger a bounded retry or an escalation to a person.

  4. 04

    Asks before it acts

    Anything that moves money, changes a record or reaches a client waits for a named person to approve it. The agent prepares the work and a person signs it off.

    Approval is a first-class step. Actions are drafted as proposals with evidence attached, routed by risk tier and executed only after sign-off. The approver, the time and the exact change are written to an append-only log.

How several agents work together

Bigger tasks are split the way an investment team splits them. A reader pulls the facts out of the documents. An analyst runs the numbers with the firm's own tools. A checker re-tests the work against the sources, and a drafter writes it up. A coordinating agent, the orchestrator, hands out the work and keeps track of what is done. The checker is kept apart from the agents whose work it reviews, so it never grades its own answers. Nothing that matters leaves the system until a person approves it.

An orchestrator plans the run and dispatches scoped workers for reading, analysis and drafting, each with its own tools, context and step budget. Independent work fans out in parallel and is merged by the orchestrator. A separate verifier, with its own context and read access to the sources, re-checks every figure and citation before anything is promoted. The output of a run is a proposal with evidence attached, and it executes only after a named approver signs off.

Fixed workflows and planning agents

When the steps are always the same, as with a capital call or a monthly reconciliation, I fix the order in advance and let the model do only the reading and writing. Agents plan their own steps only when the task changes from case to case, such as a research question. Every decision a model makes is another place where a small error can grow, so fewer model decisions means fewer places for things to go wrong.

Where the path is known, the control flow lives in code and the model is called at fixed points with typed inputs and outputs. Planning is reserved for tasks whose steps vary with the input, and even then it runs inside step and token budgets with explicit stop conditions. If each model decision is right 98% of the time, twenty chained decisions are all right only about two times in three. Moving decisions out of the model and into code is the most reliable way to raise the success rate of a whole run.

Where it's used

Portfolio monitoring

Agents check the book against its limits every day and draft the trades that would fix a breach.

Scheduled runs test positions against mandate rules through governed views, then size a proposed fix and pre-check it before it reaches the review queue.

Research

Agents gather what changed for a manager or a market and write a short brief with its sources.

Retrieval over internal notes and filings with metadata filters, summarized into a cited brief, with any uncited claim withheld.

Reconciliation

Agents match statements to the books and explain each break they find.

Entity resolution against master data, tolerance-based matching and roll-forward checks, with every break written up as an exception with evidence.

Memo drafting

Agents pull the numbers and write a first draft for the committee, with every figure linked to its source.

Figures come from tool calls and are placed into a draft where each number carries a citation to its source row or page.

How I build it

How the work is split

A reader, an analyst, a checker and a drafter, each with one job, and a coordinator that hands out the work and keeps track of it.

An orchestrator with scoped workers, each with its own tools and budget, an independent verifier, and parallel fan-out where steps do not depend on each other.

What usually goes wrong

Small mistakes snowball over a long task. Answers can sound more certain than they are, and agents can get stuck in loops that waste time and money.

Errors compound over long runs. Tool calls arrive with malformed arguments. Agents loop, token spend runs away, and the context drifts from the original task.

How I handle it

Every step is followed by a hard check, and each run has a limit on time and cost. Work the system is unsure about goes to a person before anything happens.

Tool calls are validated against their contracts before they run, and every run has step and token budgets. Low-confidence work is escalated to a reviewer. Each run leaves a replayable trace, and past runs are kept as regression tests.

How I measure it

How often a task finishes correctly, how often a person has to step in, and what each run costs and how long it takes.

Task success rate, tool-call validity, escalation rate, agreement with reviewers, and cost and latency at the median and the 95th percentile.

An example workflow: a capital call

How an agentic system handles one routine task from inbox to books, with a person in charge of the only step that moves money.The same task as a run: trigger, extraction, controls, proposal and execution, each step traced and replayable.

  1. 1

    A notice arrives

    A GP emails a capital call notice. The system picks it up from the shared mailbox within minutes.

    A Microsoft Graph subscription on the operations mailbox triggers the run. The attachment is classified and de-duplicated by content hash, so a resent notice is processed once.

  2. 2

    Read and match

    It reads the amount, due date and wire details, matches them to the right fund and commitment in the books and checks the amount against the unfunded commitment.

    Typed extraction with citations, entity resolution of fund and LP names against master data, and reconciliation of the requested amount against the commitment ledger through a SQL tool.

  3. 3

    Check the cash

    It checks the amount against cash on hand and the liquidity plan and flags anything unusual, such as changed wire instructions.

    Rule checks on unfunded balance, due-date window and liquidity buffer, plus an anomaly check on bank details. Any change to wire instructions blocks automation and forces a call-back control.

  4. 4

    Prepare the work

    It drafts the cash movement and the accounting entry, with the notice attached and every number linked to its source.

    A proposal record with evidence, citations and a risk tier is written to the queue and sent to the approver as an approval card with approve and reject actions.

  5. 5

    A person approves

    Operations reviews and approves. The system books it, files the notice and updates the pacing model.

    On approval, idempotent writes go to the accounting system and the warehouse, the pacing model refresh is scheduled and the run trace is sealed in the audit log.

Human in the loop

Every system I build keeps investment professionals in charge. The agents do the reading, checking and drafting. People review the flags, make the judgment calls and approve anything that moves money, changes a record or reaches a client. Every review is recorded with who made it and why, and each correction becomes a new test. The system learns from the team's judgment, and the final word always belongs to a person.

Human-in-the-loop is designed in from the first step. Low-confidence fields and failed checks go to a review queue, actions are gated by risk tier and delivered as approval cards in Outlook, and the reviewer's identity, decision and rationale are written to the append-only log. Reviewer corrections flow back into the verified test set and the regression suite. Autonomy is widened only when measured agreement with reviewers supports it, and it can be narrowed again at any time.

02

Document intelligence

Investment teams spend hours copying numbers out of PDFs. My systems read the documents, pull out the figures and terms a team needs and link every value to the page and line it came from, so a reviewer can check any number in seconds.

Layout-aware parsing and schema-first extraction into typed fields, with span-level citations, cross-document reconciliation and review routing for low-confidence values.

Which documents, and what gets pulled

DocumentWhat gets pulled
Limited partnership agreementsFees, carry and hurdle, commitment period, key person and removal terms
Side lettersFee discounts, most favoured nation rights, and reporting or excuse rights that change the LPA for one LP
Capital account statementsOpening and closing NAV, contributions, distributions, fees, gains and unfunded commitment
Quarterly reportsHoldings, valuations, portfolio company metrics and the GP's commentary
Due diligence questionnairesAnswers on team, process, risk, operations and compliance, matched to the firm's own questions
Confidential information memorandaRevenue, EBITDA, margins, debt and the terms of a co-investment or acquisition

A worked example: one capital account statement

The illustration at the top of this section follows one statement through these four steps.

  1. 01

    Find the parts

    The system finds the parts of the page that matter, such as the summary table and the notes under it.

    Layout analysis segments the page into regions and rebuilds the table, including rows that continue onto the next page.

  2. 02

    Pull the fields

    It pulls opening NAV, contributions, distributions, gains and closing NAV, each with the page and line it came from.

    Each target field gets a typed value with its unit, currency and period, plus the span it was read from, such as p2:L14.

  3. 03

    Check the numbers

    It checks that opening NAV plus contributions minus distributions plus gains equals closing NAV, and that the figures agree with the quarterly report.

    The roll-forward identity is tested within a tolerance, and contributions are reconciled against the commitment ledger and the GP's quarterly report.

  4. 04

    Hand over

    Values that tie are ready to use. Anything that fails, or that the system is unsure about, goes to a person with the page already open.

    Fields that pass are promoted with their citations. Failures and low-confidence values go to a review queue with the source span highlighted.

How I build it

How the work is split

One step finds the parts of each page, one pulls the values, and one checks them against the source and against other documents. A person reviews the exceptions.

Layout parsing, field extraction, citation verification and cross-document reconciliation run as separate stages with their own checks, and exceptions go to a review queue.

What usually goes wrong

Scanned PDFs, tables split across pages and footnotes that change what a number means. Side letters override the LPA, NAVs are restated after the fact, and every GP uses its own template.

OCR noise on scanned pages, tables broken across page boundaries, footnotes that redefine a figure as net or gross or switch its currency, side-letter terms that supersede the LPA, restated NAVs, and template variance across GPs.

How I handle it

I decide the fields before reading anything, and every value gets its page and line. Numbers are checked across documents, so opening NAV plus calls minus distributions plus gains has to equal closing NAV. Values the system is unsure about go to a person.

Target fields are defined before extraction, and every value carries a span-level citation that must resolve to text containing it. Roll-forward and cross-document checks run on every statement, side-letter terms are applied over the LPA, restatements are kept as new versions, and low-confidence values are routed to review.

How I measure it

How many values are right for each field and for each GP's template, how often the page and line reference is correct, and how many planted errors are caught.

Field-level accuracy within tolerance, broken out by field and by GP template, citation accuracy, and recall on planted errors next to the false-flag rate.

Results on the demos

How these are measured
Extraction accuracy
Share of verified fields where the extracted value matches the confirmed answer within a stated tolerance.
Citation coverage
Share of extracted values whose page and line reference points to text that actually contains the value.
Planted issues caught
Errors placed in the documents on purpose, such as a wrong fee or a broken roll-forward, that the system flagged for review.
False-flag rate
Share of clean checks that were flagged anyway. A useful system keeps this near zero so reviewers trust the flags.

03

Data foundations

Models and agents are only as good as the numbers they read. I bring portfolio, accounting, market and document data into one tested, reconciled place, so every system works from the numbers the investment and operations teams sign off on.

A layered warehouse with tested transformations, lineage and governed views, so every agent and model reads the same reconciled numbers through typed tools.

Sources

Portfolio and accounting systems, fund administrators, market data vendors and the data extracted from documents. Each one arrives on its own schedule, in its own format and with its own names for the same funds.

Batch and incremental loads from portfolio and accounting systems, administrator files, market data feeds and extracted document data, each landed with its load time and source identifier.

Raw, clean and reconciled

  1. 01

    Raw

    Data exactly as it arrived, kept so any number can be traced back to the file it came from.

    Immutable landing tables, partitioned by source and load time and never edited in place.

  2. 02

    Clean

    Names, units, currencies and dates made consistent, with every fund and GP matched to one master list.

    Typed, deduplicated models in dbt with entity resolution against the master, unit and currency normalization, and tests on keys and nulls.

  3. 03

    Reconciled

    Numbers checked against each other and against the administrator. This is the layer people and agents use.

    Reconciliation models that tie positions, cash and NAV across sources, with breaks raised as exceptions and governed views exposed to agents.

How I build it

How the work is split

Each load lands as it arrived, is cleaned and matched, and is then checked against the other sources before anyone reads it.

Airflow schedules loads into the raw layer, dbt builds the clean and reconciled layers, tests gate each promotion, and agents read governed views through typed tools.

What usually goes wrong

The same fund is named three different ways and numbers are restated after the fact. Feeds go stale without anyone noticing, and internal systems disagree with the administrator.

Entity duplication across sources, late restatements that overwrite history, stale feeds, and breaks between the internal books and administrator records.

How I handle it

I keep one master list of funds and GPs, and keep history both as first reported and as corrected. Every load runs freshness and reconciliation tests. Agents read only approved views, and each user sees only what they are allowed to see.

An entity master with stable identifiers, bitemporal history that keeps as-reported and as-corrected values, freshness and reconciliation tests on every load, and agents restricted to governed views with row-level permissions per user.

How I measure it

How many reconciliation breaks are open, how fresh each source is, and how quickly any number can be traced to its source.

Open reconciliation breaks and their age, freshness against each source's agreed schedule, test pass rates per load, and time to trace a reported figure to its source row through lineage.

04

Running it in production

The engineering that makes these systems safe to rely on.

Grounded answers

Every answer comes with the passage it rests on, so nobody has to trust a summary they cannot check. If the system cannot find support in the documents, it says it does not know.

Hybrid retrieval, keyword and vector search together, over chunked documents with metadata filters by fund, period and document type, then reranking. Generation is limited to retrieved passages, and an answer without a resolving citation is withheld.

Typed, checked outputs

Numbers come out in the right units and periods, ready to drop into a model or a report. Nothing is quietly filled in when a value is missing.

Extraction targets typed fields with explicit units, currency and period. Outputs are validated before anything uses them. A field that fails is retried a bounded number of times with the error attached, and then routed to a person.

The right model per task

Fast, inexpensive models handle routine work. The strongest models handle the hard reading. That keeps quality high and the bill predictable.

Per-task routing on measured accuracy, cost per document and latency at the median and the tail. Context caching for long documents, batch runs for overnight volumes and a token budget per workflow with alerts when it is exceeded.

Inside Microsoft 365

People use the tools where they already work, in Outlook and SharePoint. Nobody has to learn a new app or copy files around.

Copilot agents that read SharePoint, OneDrive and Outlook through Microsoft Graph on behalf of the signed-in user, so the model sees only what that person can open. Approvals arrive as actionable messages in Outlook and their outcome is logged.

Data stays in the firm

Sensitive data stays inside the firm's own cloud and never trains anyone else's model.

Private networking, managed secrets and encryption keys in the firm's Azure or AWS tenant, with zero-retention terms on hosted model endpoints. Personal data is redacted before any call that leaves the tenant, and open-weight models run in-tenant when data cannot leave at all.

Observability

Every run can be traced, costed and replayed after the fact, which is what auditors and risk teams ask for first.

Structured traces per run with model, version, inputs, outputs, tools called, latency and cost. Dashboards per workflow, and alerts when accuracy on live spot checks, cost or response time moves outside agreed bands.

Reliability

If a model provider has an outage, the work still gets done.

Timeouts, retries with backoff and jitter, provider and model fallbacks, durable queues and idempotent actions, so a failed step can be rerun without posting anything twice.

Release discipline

Nothing changes in production until it passes the tests, and every change can be undone.

Verified regression sets run in CI on every change. A new model runs in shadow next to the current one before any switch, and every release has a documented rollback.

How I pick the right model

Each task gets the model that fits it. I judge every candidate on accuracy on the firm's own documents, cost per document, speed and where the data is allowed to go. Frontier models like Claude and OpenAI's models take the long documents and the hard reasoning. Open-weight models run where data has to stay inside the firm or where volume makes cost the deciding factor. No model goes into production, and none gets swapped in, until it beats the current one on a verified test set.

For each candidate I run the verified test set and record field accuracy, citation accuracy, tool-call validity, latency at the median and the tail, and cost per document. Long-context frontier models handle full LPAs and reasoning across several documents. Smaller, faster models handle classification, routing and first-pass extraction. Open-weight models run in-tenant for restricted data, sized to the hardware the firm has. Structured outputs and tool calls are checked on every call whatever the model, and a model is promoted only when it wins on the verified test set at an acceptable cost.

What makes it production-grade

  • Tested against verified answers before every release
  • Human approval on anything that moves money or reaches a client
  • Full audit trail of every action and every model output
  • Access limited to the data each user is allowed to see
  • Cost and response time monitored per workflow
  • Fallbacks when a model or provider is down

05

From idea to production

I build each system all the way through, from the first conversation with the team to a production system they rely on. A human stays in the loop at every stage.The full lifecycle I run on every system, with the human review points designed in from the first step.

  1. 01

    Frame the decision

    I sit with the team to understand the decision, the documents behind it and where the hours go today. We agree what a good outcome looks like and who signs off.

    A written spec of inputs, outputs, tolerances and failure modes, the approval points, and a split between the steps that must stay deterministic and the steps that need a model.

  2. 02

    Design the system

    I design how the agents, the firm's data and the people fit together, including exactly where a person reviews and approves.

    Workflow and agent design, typed tool contracts, data access scoped to each user's permissions, a risk tier for every action and the approval gate attached to it.

  3. 03

    Build and connect

    I build the agents and connect them to the documents, data and tools the team already uses, including Outlook and SharePoint.

    Agents on the Claude Agent SDK with Model Context Protocol tools, governed data views in Snowflake or PostgreSQL and Microsoft Graph for mail and files, deployed in the firm's own tenant.

  4. 04

    Test against known answers

    Before anyone relies on it, the system is tested on real documents where the right answers are already known and confirmed by the team's experts.

    Expert-verified gold sets with planted errors, scored on accuracy, citation coverage, recall and false flags, with the regression suite running in CI.

  5. 05

    Run alongside the team

    For a few weeks the system works next to the team without acting. People compare its work with their own and correct it, and every correction makes it better.

    Shadow mode with observe-only permissions. Agreement with reviewers is tracked per field and per action, and reviewer corrections are added to the test set.

  6. 06

    Launch with a human in the loop

    It goes live with a person approving every action that matters. The system prepares the work and the evidence, and the professional makes the judgment.

    Risk-tiered autonomy. Low-risk steps run on their own, anything touching money, records or clients waits for approval with evidence attached, and every decision is logged.

  7. 07

    Operate and improve

    After launch I keep measuring. Reviews and corrections from the team feed back into the tests, so the system keeps getting more accurate and nobody has to trust it blindly.

    Monitoring of accuracy on live spot checks, cost and latency, alerts on drift, retesting on every change and a rollback path for every release.
