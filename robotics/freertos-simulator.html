FreeRTOS Kernel Simulator

LIVE

A fixed-priority preemptive FreeRTOS scheduler: higher number = higher priority, priority 0 is reserved for the idle task, equal priorities share the CPU by 1-tick round-robin slices, and mutexes optionally apply the priority-inheritance protocol (mutexes only: never semaphores or queues).

Guide: FreeRTOS Kernel Simulator

1 · What this models

A fixed-priority preemptive kernel in the style of FreeRTOS v10/v11. Every tick the kernel releases due periodic jobs, expires delays, then runs the highest-priority ready task; equal-priority tasks share the CPU with a 1-tick round-robin slice (configUSE_TIME_SLICING = 1). Priorities are 0–7 (configMAX_PRIORITIES = 8), higher number = higher priority, and priority 0 is reserved for the idle task (tskIDLE_PRIORITY), so application tasks use 1–7. The tick rate defaults to 1000 Hz (configTICK_RATE_HZ) and is selectable down to 100 Hz.

2 · Task states

Running
Holding the CPU. Exactly one task (or the idle task) runs at a time on this single core.
Ready
Runnable and queued. The scheduler picks the highest priority, oldest-ready-first within a priority.
Blocked
Waiting with a timeout or forever: vTaskDelay / vTaskDelayUntil, xSemaphoreTake, xQueueReceive.
Suspended
Removed from scheduling by vTaskSuspend until vTaskResume. Use the pause icon in the statistics table.

3 · Priority inversion and inheritance

Bounded inversion is normal: a high-priority task waiting on a mutex held by a low-priority task waits at most for the critical section. It becomes unbounded when a medium-priority task, which needs nothing from the mutex, preempts the holder, so the high-priority task now waits for unrelated work. That is the Inversion preset, and the red banner and red Gantt outline mark the ticks where it is active.

The priority-inheritance protocol raises the mutex holder to the priority of its highest waiter and restores its base priority on the give. FreeRTOS implements this for mutexes only (xSemaphoreCreateMutex); binary and counting semaphores and queues have no owner, so they cannot inherit, which is why the Prod-Con preset shows no inheritance.

4 · Utilisation and deadlines

Each periodic task has a period T and a worst-case execution time C, with an implicit deadline D = T. The scheduler load is U = Σ Ci/Ti. Liu & Layland's rate-monotonic bound is n(21/n − 1): 0.828 for n=2, 0.780 for n=3, tending to ln 2 ≈ 0.693. Below the bound, RM priority assignment is guaranteed schedulable; between the bound and 1.0 it may still work (test it here); above 1.0 misses are unavoidable, which is what the Deadline preset shows at U = 113%.

5 · Cost model

A PendSV context switch on a Cortex-M4F costs roughly 84 cycles ≈ 0.50 µs at 168 MHz. The simulator counts switches and reports the accumulated overhead analytically; it does not steal ticks, because a switch is far shorter than one 1 ms tick.

How to Use This Simulator

STEP 1

Select a Preset

Choose a scenario from the top bar: Basic (rate-monotonic, U=57%), Inversion, Inheritance, Deadline (U=113%) or Prod-Con.

STEP 2

Play the Simulation

Press Play or Space to start. Use Step for tick-by-tick execution to study each scheduling decision.

STEP 3

Watch the Gantt Chart

Observe the Gantt chart fill as tasks execute, get preempted, and block on resources. Colors show each task's state.

STEP 4

Toggle Priority Inheritance

Load the Inheritance preset, or switch on Priority Inheritance during the Inversion preset and press Reset: the mutex holder is raised to its waiter's priority, so the medium task can no longer preempt it. Mutexes only, semaphores never inherit.

STEP 5

Experiment

Add custom tasks, mutexes, and semaphores to build your own scenarios and learn scheduling behavior.

Methodology & assumptions

What this models

A tick-driven FreeRTOS-style kernel on a single core. Each tick the simulator expires delays, releases the periodic jobs whose period elapsed, then dispatches the highest-priority ready task; equal priorities rotate on a one-tick round-robin slice. Tasks share a mutex (with an optional priority-inheritance protocol) and a counting semaphore, and every scheduling decision is written to the event log, the Gantt chart and the per-task statistics from the same tick record, so the three always agree.

Key assumptions

  • Priorities 0–7 (configMAX_PRIORITIES = 8), higher number = higher priority; priority 0 is the idle task (tskIDLE_PRIORITY), so application tasks use 1–7.
  • Tick rate 1000 Hz by default (configTICK_RATE_HZ), selectable 100 / 250 / 500 / 1000 Hz; one tick is the scheduling quantum.
  • Preemptive with time slicing: configUSE_PREEMPTION = 1, configUSE_TIME_SLICING = 1, slice = 1 tick.
  • Context switch modelled at 84 cycles ≈ 0.50 µs on a 168 MHz Cortex-M4F; the overhead is reported analytically and does not consume a tick.
  • Periodic tasks have implicit deadlines D = T; a job still owing CPU at its next release is a deadline miss.
  • Presets: Basic U = 0.567; Inversion / Inheritance U = 0.667 with a 6-tick critical section on Mutex_SPI; Deadline U = 1.133; Producer/Consumer U = 0.808 on a counting semaphore of length 5.
  • Fully deterministic: no random number generator, so the same preset always produces the same trace.

Formulas & references

  • Scheduler load U = Σ C_i / T_i; rate-monotonic sufficient bound n(2^(1/n) − 1) → 0.828 (n=2), 0.780 (n=3), ln 2 ≈ 0.693 as n→∞.
  • Measured CPU busy = 1 − idle ticks / elapsed ticks; per-task share = run ticks / elapsed ticks.
  • Priority inheritance: on block, holder.priority = max(holder.priority, waiter.priority); on xSemaphoreGive the holder returns to its base priority. Mutexes only, semaphores and queues have no owner.
  • Switch overhead = switches × 84 / 168 MHz.

Limitations

  • Time is quantised to whole ticks: sub-tick execution, tick-ISR jitter, interrupt latency and ISR-to-task handoff are not modelled.
  • No stacks, heap, configTOTAL_HEAP_SIZE, queue payloads, event groups, task notifications, software timers or tickless idle.
  • Priority inheritance is single level: nested mutexes, transitive inheritance and the priority-ceiling protocol are not implemented, and deadlock is not detected.
  • One mutex and one semaphore action per task per job; critical sections are a fixed number of ticks rather than data dependent.
  • WCRT is the worst response observed in this run, not an analytic worst case; C is a fixed budget, not a measured WCET.
  • Single core, no SMP, no cache or flash wait-state effects, and the switch cost is a stated constant rather than a measurement.
