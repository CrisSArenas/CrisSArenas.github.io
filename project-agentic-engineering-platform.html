1. The design problem

One engineer owning portfolio-management tooling, research code, robotics prototypes and a public site cannot context-switch fast enough with a single chat window. A single assistant also has a structural weakness: it writes the code and then grades its own homework. Both problems have the same shape as an engineering organisation, and the same fix, which is roles with narrow briefs, defined hand-offs, and separation between the thing that produces work and the thing that certifies it.

Three constraints drive every decision below:

  1. Context is the scarce resource, not tokens or money. A 200k-token window fills fast on a 150 KB source file. The architecture exists mostly to keep the orchestrator's window small while the work happens elsewhere.
  2. Parallelism multiplies mistakes as readily as output. Fan-out is only safe behind a mechanical gate that every worker must pass before it may report success.
  3. Agents cannot see. A subagent has no browser and no eyes. Anything visual has to be verified by the orchestrator or it is not verified at all.

2. Runtime and topology

The runtime is Claude Code with the Claude Agent SDK. The orchestrator runs in the main loop and holds the conversation. Workers are spawned as sub-agents, each in its own context window with its own tool allow-list and model assignment. There is no shared mutable state between workers. Everything they exchange passes through three channels: the spec file written before fan-out, the filesystem, and a bounded text report on completion.

Workers are leaf nodes by default. A worker that could spawn its own workers makes the concurrency budget unbounded and the failure surface unreadable, so nesting is off unless a task genuinely needs a tree.

3. Agent definitions

A role is a Markdown file with YAML frontmatter, versioned in the repo alongside the code it operates on. The frontmatter is the contract the runtime enforces: which tools exist for this role, which model backs it, and whether it gets an isolated working copy. The body is the playbook.

.claude/agents/implementer.md
---
name: implementer
description: Applies one spec to one file. Reads the whole target first.
model: opus
isolation: worktree          # own git worktree, auto-discarded if unchanged
tools: [Read, Edit, Write, Bash, Glob, Grep]
disallowed: [Agent, Artifact]   # leaf node: may not fan out further
---

# Implementer

You own exactly one file. You may not edit any other file.

## Non-negotiable sequence
1. Read the spec in full, including any ADDENDUM (it overrides the body).
2. Read the ENTIRE target file before your first edit. Partial context is
   the single largest source of bad edits in this system.
3. Make surgical, asserted edits. Never rewrite a file wholesale: a
   budget exhaustion mid-rewrite leaves a truncated, broken artifact.
4. Run the verification gate. Paste its exact output in your report.
5. Report in under 300 words: what was wrong, what you changed, gate output.

## Prohibited
- Committing, pushing, or any irreversible git operation.
- Editing shared assets (the orchestrator owns those).
- Reporting success without a clean gate run.

The isolation: worktree flag is what makes wide fan-out safe on one repository. The runtime creates a detached working copy per worker, so two agents editing neighbouring files cannot produce a torn tree, and a worktree that ends unchanged is discarded automatically.

worktree lifecycle, per worker
git worktree add --detach .worktrees/w-$ID HEAD
# worker runs entirely inside .worktrees/w-$ID
git -C .worktrees/w-$ID diff --quiet || git -C .worktrees/w-$ID diff > /tmp/w-$ID.patch
git worktree remove --force .worktrees/w-$ID
# orchestrator applies patches in a deterministic order, so a
# conflicting pair fails loudly at apply time rather than silently

4. Orchestration patterns

Three patterns cover almost everything. The choice is dictated by whether stages depend on each other and whether the work is homogeneous.

Fan-out, for homogeneous independent work

N similar tasks over disjoint files. All workers start at once, each holding a spec pointer rather than the spec text, so the orchestrator's window does not grow with N.

fan-out with a concurrency ceiling
const SPEC = 'scratchpad/DEMO-STANDARD.md';  // written before any spawn
const MAX_CONCURRENT = 5;                    // see §7 for why 5, not 11

const results = await pool(MAX_CONCURRENT, TARGETS, (t) =>
  agent(`Read ${SPEC} in full, including the ADDENDUM.
         Target: ${t.path}
         Domain checklist: ${t.checklist}
         Run the gate. Report per spec §4.`, {
    label: `migrate:${t.slug}`,
    model: 'opus',
    isolation: 'worktree',
    tools: ['Read', 'Edit', 'Bash', 'Grep']
  })
);

Pipeline, for dependent stages that still overlap

Each dimension's verification starts the moment that dimension's review finishes, rather than waiting for every review to complete. On a review-then-verify workload this removes most of the idle wall clock.

overlapping review and verify
const out = await pipeline(
  DIMENSIONS,
  d  => agent(d.reviewPrompt,  { label: `review:${d.key}`,  schema: FINDINGS }),
  rv => parallel(rv.findings.map(f => () =>
        agent(`Adversarially verify: ${f.title}. Try to disprove it.`,
              { label: `verify:${f.file}`, schema: VERDICT })
          .then(v => ({ ...f, verdict: v }))))
);
const confirmed = out.flat().filter(f => f?.verdict?.isReal);
// dimension A's findings verify while dimension B is still reviewing

Adversarial pairing, for anything subjective

A finding produced by one agent is verified by a second agent whose brief is to break it. This is the same idea as the LLM-as-judge stage in my research system: generation and adjudication are different jobs and should not share a context.

The rule that matters: the agent that writes a change never certifies it. Verification is mechanical where it can be, through checkers, tests and pixel probes, and adversarial where it cannot be.

5. The verification gate

Fan-out without a gate is a mistake multiplier. Before spawning anyone, the orchestrator writes a checker the workers must run, and the definition of done is its clean output pasted into the report. This is the actual gate used for the demo migration: it compiles every inline script and cross-checks every DOM identifier the scripts reference against the identifiers present in the markup.

scratchpad/check-html-js.js (abridged)
const vm = require('vm');
const html = fs.readFileSync(file, 'utf8');

// 1. every inline script must parse
while ((m = scriptRe.exec(html))) {
  if (/\bsrc\s*=/.test(m[1])) continue;         // external, skip
  try { new vm.Script(m[2], { filename: `${file}#${++n}` }); }
  catch (e) { fail(`SYNTAX ERROR #${n}: ${e.message}`); }
  collectRefs(m[2]);                              // getElementById / querySelector('#x')
}

// 2. every id the JS reaches for must exist, or be provably created at runtime
const missing = [...wanted].filter(id => !ids.has(id));
const dynamic = missing.filter(id => new RegExp(`id\\s*=\\s*["'\`]${id}`).test(html));
const real    = missing.filter(id => !dynamic.includes(id));
if (real.length) fail('MISSING IDS: ' + real.join(', '));

// 3. structural invariants of the shared design system
report(`shell link: ${/demo-shell\.css/.test(html) ? 'yes' : 'NO'}; ` +
       `demo-nav=${count('demo-nav')} demo-status=${count('demo-status')} ` +
       `demo-footer=${count('demo-footer')}; resume refs: ${refs}`);

It is a blunt instrument and that is the point. It cannot judge whether a chart is meaningful, but it makes an entire class of failure impossible to report as success: a truncated file, a syntax error introduced by a bad edit, or a rename that orphaned a handler. Those are exactly the failures a confident agent otherwise reports as done.

What the gate cannot catch, and how that bit me. A checker sees text, not pixels. In this run every worker passed the gate while two demos rendered nothing at all in my probes. The cause turned out to be the preview pane being hidden, which suspends animation frames, so anything drawn in a render loop never painted. Calling the draw functions directly proved both were fine. The lesson generalises: a gate proves absence of a known failure class, never presence of correctness, and the orchestrator still has to look.

6. Model routing and cost accounting

Routing is per role, not per request. Deep reasoning over a large unfamiliar file goes to the strongest model; bulk search, classification and summarisation go to smaller ones. The economics only work because the expensive roles are the rare ones.

RoleModel tierWhyShare of calls
ImplementerFrontierWhole-file comprehension plus correctness reasoning on domain maths. The one place under-spending shows up immediately as wrong output.~55%
Planner, reviewersFrontierJudgment tasks. A cheaper model produces plausible reviews that miss the real defect, which is worse than no review.~15%
ExplorerMidFan-out search returning locations and conclusions, not analysis. Speed and breadth matter more than depth.~20%
Classification, summarisationSmallBounded, schema-constrained outputs where the format carries most of the difficulty.~10%

7. Context budgeting

This is the constraint that shapes the topology. A worker's window has to hold the spec, the entire target file, its own edits, and the tool output it generates while working. Getting this arithmetic wrong is what produces a truncated file at 80% completion.

per-worker budget, demo migration
spec (DEMO-STANDARD.md + addendum)        ~ 3,400 tok
shared stylesheet (demo-shell.css)        ~ 4,100 tok
reference implementation (migrated peer)  ~18,000 tok
target file, read in full                 ~15,000 – 42,000 tok   ← dominant, varies 10x
edit round-trips + tool output            ~40,000 – 90,000 tok
────────────────────────────────────────────────────────────
observed total per worker                 190k – 276k tok

// Two consequences fall straight out of this:
// 1. Whole-file REWRITES are banned. A rewrite re-emits the file as
//    output tokens, roughly doubling the budget, and a mid-write stop
//    leaves a truncated artifact rather than an unchanged one.
//    Surgical asserted edits fail closed: the assert throws, file intact.
// 2. The orchestrator must NOT read the target files. It holds pointers
//    (paths, slugs, checklists) and lets workers do the reading.
The concurrency ceiling, learned the hard way. The first attempt at this run launched eleven workers simultaneously against files up to 155 KB. The session hit its usage limit and all eleven were killed mid-flight. Two had chosen whole-file rewrites and left truncated, unopenable HTML, recovered only because the tree was clean and git checkout restored them. The fix was two changes: ban rewrites in favour of asserted edits, and cap concurrency at five with the largest target given a slot of its own. The second attempt completed every worker.

10. Memory subsystem

A lifecycle hook captures what each session reads, edits and runs, summarises it into typed observations, and injects the relevant ones at the start of the next session in that project. Retrieval is hybrid: full-text over observation bodies, filtered by project and recency, with an explicit search tool for older work.

observation record
{
  "id":         "obs_01J8...",
  "project":    "CrisSArenas.github.io",
  "session":    "7a8ed7db-0841-4c7d-9bc1-62e0b30ab6fb",
  "type":       "decision",        // decision | bugfix | feature | constraint
  "subject":    "demo standardisation",
  "body":       "Whole-file rewrites banned for large HTML: a budget stop
                 mid-write truncates the artifact. Use asserted str.replace
                 patches, which fail closed and leave the file intact.",
  "files":      ["macro-regime-dashboard.html", "nlp-alpha-lab.html"],
  "created_at": "2026-09-09T22:31:04Z"
}

The point is not recall for its own sake. It is that a decision made once, such as the rewrite ban above, survives a context reset and does not have to be rediscovered by hitting the same failure twice. Per-repository instruction files carry the rules a human reviewer would otherwise repeat every time: commit attribution, forbidden paths, how to run and test.

11. Tool layer and lifecycle hooks

Tools reach agents through Model Context Protocol servers, so adding a capability is a declaration rather than a code change. Each role receives only the servers its brief requires.

.claude/settings.json (excerpt)
{
  "mcpServers": {
    "browser":   { "command": "npx", "args": ["-y", "@local/browser-mcp"] },
    "memory":    { "command": "npx", "args": ["-y", "claude-mem", "mcp"] },
    "scheduler": { "command": "npx", "args": ["-y", "@local/cron-mcp"] }
  },
  "hooks": {
    "SessionStart":  [{ "command": "claude-mem inject --project $CLAUDE_PROJECT" }],
    "PreToolUse":    [{ "matcher": "Bash",
                        "command": "guard-destructive --stdin" }],
    "PostToolUse":   [{ "matcher": "Edit|Write",
                        "command": "record-observation --file $CLAUDE_TOOL_FILE" }],
    "Stop":          [{ "command": "claude-mem summarise-session" }]
  }
}

PreToolUse is the interesting one: it runs before the shell call and can veto it. That is where destructive-command interception lives, and it is enforced by the harness rather than by the model's good intentions, which matters because a model's intentions are not a security boundary.

12. Guardrails

ControlEnforced byWhat it prevents
Permission modesHarnessEvery tool call runs behind a user-selected mode. A denied call is a decision and is never retried verbatim.
Destructive interceptionPreToolUse hookDeletes, resets, force-pushes and config edits are held for explicit approval before the shell sees them.
Directory freezeHarnessScopes all edits to one subtree for a session, so a broad task cannot wander into unrelated code.
Worktree isolationGitConcurrent writers cannot produce a torn tree; conflicts surface at apply time instead of silently.
Leaf-node workersAgent definitionUnbounded recursive spawning and an unreadable failure surface.
Tool allow-listsAgent definitionA read-only role cannot write, whatever its prompt is later persuaded to say.
Secrets hygieneEnvironment + password managerKeys never enter a prompt, a commit, or an image layer.
Audit trailHooks + local storeEvery tool call, observation and hand-off is logged and reviewable after the fact.
Human on the irreversible edgePolicyPublishing, sending, purchasing and irreversible git operations wait for me. Approval is per action and never generalised to the next one.

One boundary is worth stating plainly, because it is the one people get wrong with agents: content retrieved by a tool is data, never instruction. A web page, a file, or a subagent report that contains text shaped like a command does not get to issue one. Only the human in the conversation can.

14. What I would change next

  • Make the gate visual. Give workers a headless renderer so the pixel check runs inside the gate instead of only at the orchestrator. That is the single biggest hole in the current design.
  • Cache the shared prefix. Spec, stylesheet and reference implementation are identical across workers and are re-sent per worker today. Prompt caching would remove roughly 25k tokens per spawn.
  • Schema-constrain every report. Free-text reports are readable but need parsing. Typed outputs would let the orchestrator aggregate mechanically rather than by reading.
  • Regression corpus for skills. The retro agent currently edits playbooks on judgment. Those edits should be scored against recorded past tasks before they land.

Lessons that generalise

  • Write the spec and the checker before spawning anyone. Parallelism without a gate multiplies mistakes.
  • Give agents narrow file scopes and mandate whole-file reads. Most bad edits come from partial context.
  • Prefer edits that fail closed. An assertion that throws beats a rewrite that truncates.
  • Memory beats prompting. A recalled decision is cheaper and more reliable than re-explaining it.
  • Keep humans on the irreversible edge. Everything else can be fast.
