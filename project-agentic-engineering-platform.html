1. The design problem

One engineer owning portfolio-management tooling, research code, robotics prototypes and a public site cannot context-switch fast enough with a single chat window. A single assistant also has a structural weakness: it writes the code and then grades its own homework. Both problems have the same shape as an engineering organisation, and the same fix, which is roles with narrow briefs, defined hand-offs, and separation between the thing that produces work and the thing that certifies it.

Three constraints drive every decision below:

  1. Context is the scarce resource, not tokens or money. A 200k-token window fills fast on a 150 KB source file. The architecture exists mostly to keep the orchestrator's window small while the work happens elsewhere.
  2. Parallelism multiplies mistakes as readily as output. Fan-out is only safe behind a mechanical gate that every worker must pass before it may report success.
  3. Agents cannot see. A subagent has no browser and no eyes. Anything visual has to be verified by the orchestrator or it is not verified at all.

2. Runtime and topology

The runtime is Claude Code with the Claude Agent SDK. The orchestrator runs in the main loop and holds the conversation. Workers are spawned as sub-agents, each in its own context window with its own tool allow-list and model assignment. There is no shared mutable state between workers. Everything they exchange passes through three channels: the spec file written before fan-out, the filesystem, and a bounded text report on completion.

Workers are leaf nodes by default. A worker that could spawn its own workers makes the concurrency budget unbounded and the failure surface unreadable, so nesting is off unless a task genuinely needs a tree.

3. Agent definitions

A role is a versioned definition stored alongside the code it operates on. Each declares a contract the runtime enforces rather than merely suggests: the tool set available to that role, the model tier backing it, whether it receives an isolated working copy, and whether it may delegate further. The body of the definition is the playbook, written as an operating procedure rather than a persona.

Making the contract machine-enforced rather than prompt-enforced is the point. A read-only reviewer with no write capability cannot modify code however its prompt is later reworded, and a leaf worker with no delegation capability cannot spawn a tree of its own. Instructions constrain behaviour; capability declarations constrain outcomes, and only the second survives an unexpected prompt.

What every builder role is required to do

  1. Read the specification in full, including any addendum, which takes precedence over the base document.
  2. Read the entire target file before the first edit. Partial context is the largest single source of bad edits in this system.
  3. Make narrow, individually asserted changes. Never regenerate a file wholesale.
  4. Pass the verification gate and reproduce its output verbatim in the report.
  5. Report within a fixed length: what was wrong, what changed, and the gate result.

Isolation

Builder roles work against a detached copy of the repository rather than the shared tree. Two agents editing neighbouring files therefore cannot produce a torn state, and an agent that changes nothing leaves nothing behind. Changes are collected and applied centrally in a deterministic order, so a genuine conflict between two workers surfaces loudly at integration instead of silently overwriting.

4. Orchestration patterns

Three patterns cover nearly all of the work. The choice follows from whether stages depend on one another and whether the tasks are homogeneous.

Fan-out, for homogeneous independent work

Many similar tasks over disjoint files, dispatched together under a concurrency ceiling. Each worker receives a pointer to the shared specification rather than its text, so the orchestrator's own context does not grow with the number of workers. This is the pattern used to rebuild the eleven demos on this site.

Pipeline, for dependent stages that still overlap

Where a second stage depends on the first, work is streamed rather than batched: each dimension's verification begins the moment that dimension's review completes, instead of waiting for every review to finish. On review-then-verify workloads this removes most of the idle wall clock without changing the dependency structure.

Adversarial pairing, for anything subjective

A finding produced by one agent is examined by a second whose brief is to disprove it. Generation and adjudication are different jobs and should not share a context, for the same reason the author of a change is a poor reviewer of it. This is the same principle as the independent adjudication step in my alternative-data platform, arrived at separately in both systems.

The rule that matters: the agent that writes a change never certifies it. Verification is mechanical wherever it can be, through checkers, tests and rendered-output probes, and adversarial wherever it cannot.

5. The verification gate

Fan-out without a gate is a mistake multiplier. Before any worker is dispatched, the orchestrator writes a checker every worker must run, and the definition of done is that checker's clean output reproduced in the report. Self-assessment is not accepted as evidence.

For the demo rebuild, the gate asserted three things about each file:

  • Every inline script parses. Each script block is compiled in isolation, so a syntax error introduced by a careless edit cannot be reported as success.
  • Every element the code reaches for exists. Identifiers referenced by scripts are resolved against the markup, with elements created at runtime accounted for separately. This catches the rename that quietly orphans a handler.
  • The shared design contract holds. Structural invariants of the common shell: exactly one navigation region, one status strip, one footer, the shared stylesheet present, and no links to pages that no longer exist.

It is a blunt instrument, deliberately. It cannot judge whether a chart is meaningful or a formula correct. What it does is make an entire class of failure impossible to report as done: a truncated file, a parse error, a dangling reference, or a page that drifted from the shared design.

What a gate cannot catch, and how that bit me. A checker reads text, not pixels. In this run every worker passed the gate while two demos appeared to render nothing at all in my probes. The cause was the preview surface being hidden, which suspends animation frames, so anything drawn in a render loop never painted. Driving the draw path directly showed both were fine. The lesson generalises: a gate proves the absence of a known failure class, never the presence of correctness, and someone with eyes still has to look.

6. Model routing and cost accounting

Routing is per role, not per request. Deep reasoning over a large unfamiliar file goes to the strongest model; bulk search, classification and summarisation go to smaller ones. The economics only work because the expensive roles are the rare ones.

ImplementerFrontierWhole-file comprehension plus correctness reasoning on domain maths. The one place under-spending shows up immediately as wrong output.~55%
Planner, reviewersFrontierJudgment tasks. A cheaper model produces plausible reviews that miss the real defect, which is worse than no review.~15%
ExplorerMidFan-out search returning locations and conclusions, not analysis. Speed and breadth matter more than depth.~20%

7. Context budgeting

This is the constraint that shapes the topology. A worker's context has to hold the specification, the entire target file, its own edits, and all the tool output it generates along the way. Getting this arithmetic wrong produces a half-finished file rather than a clean failure.

Context consumerShare of a worker's windowConsequence
Specification and shared assetsSmall and fixedIdentical across workers, which makes it the obvious candidate for caching.
Reference implementationModerate and fixedOne already-migrated peer, so every worker converges on the same conventions.
Target file, read in fullVaries roughly tenfoldThe dominant and least predictable term. Concurrency has to be sized against the largest target, not the average.
Edit cycles and tool outputLargest single shareGrows with the number of round trips, which argues for fewer, larger, asserted edits.

Two design rules fall straight out of that distribution:

  • Whole-file regeneration is banned. Regenerating a file re-emits it as output, roughly doubling the budget, and an interruption partway through leaves a truncated artifact. Narrow asserted edits fail closed instead: the assertion throws and the file is left untouched.
  • The orchestrator does not read the work files. It holds paths, slugs and checklists, and delegates the reading. The moment it starts reading targets, the coordination layer becomes the bottleneck it exists to prevent.
The concurrency ceiling, learned the hard way. The first attempt at this run dispatched eleven workers at once against files up to 155 KB. The session hit its usage limit and all eleven were terminated mid-flight. Two had chosen whole-file regeneration and left truncated, unopenable files, recovered only because the tree was clean and the previous versions were still in version control. The fix was two changes: ban regeneration in favour of asserted edits, and cap concurrency at five with the largest target given a slot of its own. The second attempt completed every worker.

9. Memory subsystem

A lifecycle hook records what each session reads, edits and runs, distils it into typed observations, and surfaces the relevant ones at the start of the next session in that project. Retrieval is hybrid: full-text over observation content, filtered by project and recency, with an explicit search path for older work.

Each observation is typed by what it represents, a decision, a defect and its fix, a new capability, or a standing constraint, and is bound to the files and the session it came from. Typing matters because the recall rule differs by kind: a decision should resurface whenever the same area is touched again, while a defect record is mostly useful when the same symptom reappears.

The value is not recall for its own sake. It is that a decision made once survives a context reset instead of being rediscovered by hitting the same wall twice. The regeneration ban in the previous section is exactly that kind of record: learned through a failure, written down, and now applied automatically rather than relearned. Per-repository instruction files carry the standing rules a human reviewer would otherwise repeat every time, such as commit conventions, protected paths, and how to run and test the project.

Alongside it, a knowledge graph over the codebase answers structural questions, how components relate and where responsibility for a behaviour actually lives. That is the class of question text search answers badly and an explorer agent would otherwise burn context rediscovering.

10. Tool layer and lifecycle hooks

Capabilities reach agents through a standard tool-server protocol, so adding one is a declaration rather than a code change, and each role receives only the servers its brief requires. The current set covers shell and filesystem access, a headless browser, the memory store, and scheduled execution.

Lifecycle hooks are where policy is actually enforced, and they matter more than the tool list because they run outside the model's control:

Lifecycle pointWhat runs thereWhy it has to be a hook
Session startRelevant prior observations are injected into context.Onboarding cost has to be paid automatically, or it will not be paid at all.
Before a tool callDestructive shell operations are intercepted and held for approval.It fires before execution and can veto. A model's stated intention is not a security boundary; an interceptor is.
After a file changeThe change is recorded as an observation with its context.Capture must be automatic, because an agent asked to remember something reliably forgets to.
Session endThe session is summarised into durable memory.The summary has to outlive the context that produced it.

11. Guardrails

ControlEnforced byWhat it prevents
Permission modesHarnessEvery tool call runs behind a user-selected mode. A denied call is a decision and is never retried verbatim.
Destructive interceptionPre-execution hookDeletes, resets, force-pushes and config edits are held for explicit approval before the shell sees them.
Directory freezeHarnessScopes all edits to one subtree for a session, so a broad task cannot wander into unrelated code.
Worktree isolationGitConcurrent writers cannot produce a torn tree; conflicts surface at apply time instead of silently.
Leaf-node workersAgent definitionUnbounded recursive spawning and an unreadable failure surface.
Tool allow-listsAgent definitionA read-only role cannot write, whatever its prompt is later persuaded to say.
Secrets hygieneEnvironment + password managerKeys never enter a prompt, a commit, or an image layer.
Audit trailHooks + local storeEvery tool call, observation and hand-off is logged and reviewable after the fact.
Human on the irreversible edgePolicyPublishing, sending, purchasing and irreversible git operations wait for me. Approval is per action and never generalised to the next one.

One boundary is worth stating plainly, because it is the one people get wrong with agents: content retrieved by a tool is data, never instruction. A web page, a file, or a subagent report that contains text shaped like a command does not get to issue one. Only the human in the conversation can.

13. What I would change next

  • Make the gate visual. Give workers a headless renderer so the pixel check runs inside the gate instead of only at the orchestrator. That is the single biggest hole in the current design.
  • Cache the shared prefix. Spec, stylesheet and reference implementation are identical across workers and are re-sent per worker today. Prompt caching would remove roughly 25k tokens per spawn.
  • Schema-constrain every report. Free-text reports are readable but need parsing. Typed outputs would let the orchestrator aggregate mechanically rather than by reading.
  • Regression corpus for skills. The retro agent currently edits playbooks on judgment. Those edits should be scored against recorded past tasks before they land.

Lessons that generalise

  • Write the spec and the checker before spawning anyone. Parallelism without a gate multiplies mistakes.
  • Give agents narrow file scopes and mandate whole-file reads. Most bad edits come from partial context.
  • Prefer edits that fail closed. An assertion that throws beats a rewrite that truncates.
  • Memory beats prompting. A recalled decision is cheaper and more reliable than re-explaining it.
  • Keep humans on the irreversible edge. Everything else can be fast.
